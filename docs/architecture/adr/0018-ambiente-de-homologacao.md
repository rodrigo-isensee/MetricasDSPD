# 0018 - Ambiente de homologação: branch `homolog`, Compose isolado em loopback e suíte de homologação portátil
- Status: **proposta** (aguarda as respostas H-1 a H-8 do plano `features/homologacao.md` §10)
- Data: 2026-10-12
- Substitui parcialmente: ADR 0010 (linha "homologação" da tabela de ambientes e o job `deploy` para homologação), ADR 0014 §"Execução" (passa a haver um segundo projeto Compose). A linha "homologação" da ADR 0013 continua sendo o alvo de nuvem futuro.
- Não muda: custo zero (ADR 0014), loopback até o SSO (D-1), webhook desligado (D-2), a `main` é do usuário, o portão de code review e QA por entrega.
- Plano técnico: [`features/homologacao.md`](../features/homologacao.md)

## Contexto
O usuário pediu "um ambiente e uma branch para homologação; sempre vamos subir para homolog, rodar mais testes, e só depois vai para a `main`". Restrições: nada pago, nenhuma hospedagem disponível, a única máquina é um notebook WSL com 8 GB (tarefas pesadas uma de cada vez, homologação pesada de madrugada), migração para um Git corporativo em breve (o desenho tem de funcionar igual lá), dados ainda mockados. Hoje o PR roda lint, tipos, cobertura, `test:pg`, build, gate e E2E da SPA contra `vite preview` com o mock no navegador; nada testa a pilha implantada (nginx → API → PostgreSQL com papéis reais), a migração a partir do estado da `main`, nem backup e restauração.

## Decisão
1. **Branch `homolog`, de longa duração, entre as branches de trabalho e a `main`.** PRs de `feature/`, `fix/`, `docs/`, `chore/`, `refactor/` (criadas a partir da `main`) têm base `homolog`. Code review e QA continuam no PR, como hoje. Depois do merge em `homolog` roda a **suíte de homologação**; com ela verde, abre-se o PR de release `homolog` → `main`, que o usuário valida e mescla. Após o merge, `homolog` é avançada até a `main` (fast-forward). A `homolog` nunca é reescrita (sem force push); reverter é `git revert -m 1`.
2. **A lógica fica em scripts, não no CI.** `scripts/homolog/*.sh`, expostos como `pnpm homolog:*`, fazem tudo (implantar, semear, testar, medir, fazer backup e restaurar). Workflows de CI e agendadores só chamam os scripts. Trocar de GitHub para o Git corporativo é reescrever um arquivo de pipeline de ~30 linhas, não a homologação.
3. **O ambiente persistente roda na máquina do usuário**, como um segundo projeto Docker Compose (`-p metricasdspd-homolog`), separado do de desenvolvimento: volume, rede e banco próprios, portas próprias **só em 127.0.0.1** (web 18080, API 13000, Postgres 15432), segredos próprios em `.env.homolog` (fora do git), imagens marcadas com o SHA implantado. O código implantado é sempre um **snapshot de `origin/homolog`** exportado com `git archive` (nunca a árvore de trabalho), então o que está em homologação é exatamente o que está no remoto.
4. **Dois executores da mesma suíte:**
   - **Efêmero no CI hospedado** (agora, com mock): workflow `homolog` em `push` para `homolog` sobe a pilha num runner hospedado gratuito, roda a suíte inteira e descarta. É o portão automático e não pesa no notebook.
   - **Local, noturno** (sempre disponível; obrigatório quando houver dado real): o agendador do Windows chama `pnpm homolog:noite` de madrugada; o script confere a memória e a carga antes, atualiza o ambiente persistente se `origin/homolog` mudou e roda a suíte uma etapa pesada por vez. `pnpm homolog:subir` faz só a implantação, sob demanda.
   Dado real **nunca** vai ao runner hospedado: com integração real, o executor efêmero continua só com o mock e a suíte com dado real roda só no local (ou, no futuro, em infraestrutura corporativa, com os mesmos scripts).
5. **Dados:** agora, seed mock determinístico (`gerarBaseMock`, semente e data âncora fixas, as mesmas do CI), aplicado sobre o banco persistente. Cópia ou carga real só depois de D-5 (retenção e eliminação), I-13 e de uma decisão explícita do usuário, e somente no executor local.

## Alternativas consideradas
- **Runner self-hosted no notebook (GitHub ou corporativo).** Prós: deploy automático real ao mesclar. Contras: workflow do repositório executa na máquina do usuário com acesso ao `.env` e ao Docker (equivalente a root); em repositório público, PRs de fork podem chegar a ele; é mais um serviço de longa duração consumindo memória. Rejeitado agora; reavaliar em infraestrutura corporativa, onde ele seria o caminho natural (ADR 0010, I-9).
- **GitHub Environments + job de deploy.** Prós: segredos por ambiente, histórico de implantação. Contras: não há alvo para implantar (sem hospedagem); revisores obrigatórios em repositório privado exigem plano pago; não existe no Git corporativo com o mesmo nome. Usável só como rótulo no executor efêmero; não é a base do desenho.
- **Codespaces.** Prós: 2 núcleos e 8 GB fora do notebook, cota gratuita mensal. Contras: não é persistente (hiberna após inatividade), cota pessoal acaba, portas passam por autenticação do GitHub, some na migração para o Git corporativo. Rejeitado.
- **Hospedagem gratuita (Render, Fly.io, Oracle Always Free, Railway).** Prós: URL compartilhável. Contras: viola D-1 (sem SSO, o ambiente ficaria na internet), terceiro guarda os dados (LGPD quando houver dado real), camadas gratuitas mudam sem aviso. Rejeitado.
- **Só o executor local, sem CI.** Prós: um lugar só. Contras: tudo pesa no notebook; homologação para se a máquina estiver desligada. Fica como modo de contingência se o Git corporativo não tiver runners.
- **Só o executor efêmero, sem ambiente persistente.** Prós: zero memória local. Contras: o usuário não tem onde abrir e validar à mão; não testa migração sobre um banco que viveu releases anteriores. Rejeitado como único executor.
- **Homologação no mesmo projeto Compose do dev, com outro database.** Prós: um Postgres a menos. Contras: `db:reset` do dev apaga a homologação, o mesmo superusuário e as mesmas senhas, portas conflitam. Rejeitado.

## Consequências
- **Mais fácil:** testar a pilha implantada de verdade (nginx, proxy, papéis e GRANTs, migração sobre estado anterior, backup e restauração) sem gastar nada; mudar de Git sem refazer a homologação; reproduzir localmente qualquer falha do CI com o mesmo comando.
- **Mais difícil:** um passo a mais até a `main` (release em lote); um segundo conjunto de imagens e um volume no disco do WSL; reverter uma feature já em `homolog` exige `revert` e, para reintroduzi-la, "revert do revert".
- **Riscos:** notebook desligado ou suspenso de madrugada (a suíte noturna não roda; o executor efêmero cobre enquanto houver CI); execução noturna disputar memória com algo esquecido aberto (o script aborta pelo teto do Jarvis); `homolog` divergir da `main` (verificação no script e no PR de release); migração aplicada em homologação e depois rejeitada (restauração do backup pré-implantação, ver plano §4).
