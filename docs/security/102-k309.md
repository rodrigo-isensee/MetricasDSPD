## Detalhe dos achados
**A1, bloqueante (severidade média; esforço P; dono: devops-engineer).** Evidência em `docs/devops/102-k309-pre-push-proposto.md:340`: `awk ... docs/devops/102-k309-pre-push-proposto.md > .githooks/pre-push && chmod ...`. O shell trunca o destino antes do awk rodar. Se o documento não existe na árvore, o awk falha (rc=2) e a cadeia `&&` para, mas o arquivo já está vazio e mantém o bit de execução do original. Isso acontece, por exemplo, quando o dono segue a instrução da seção 3 e cria `chore/k309-pre-push` a partir da develop antes de este documento entrar nela. O mesmo vale para um marcador `bash pre-push` renomeado numa versão futura do documento. O git executa o hook vazio pelo shell, com rc 0, e o envio para a main passa (S1). O controle da `R-MAIN` cai em silêncio, porque o `git diff --stat` do fim da cadeia nem chega a rodar. A proteção da main no GitHub continua de pé, e por isso a severidade é média, não alta. Mas o hook é a trava local que a regra exige, e o defeito está justamente no passo que o brief manda conferir. Há ainda um efeito menor: o comando lê o documento da árvore de trabalho, não da versão revisada, então qualquer edição posterior do documento muda o hook aplicado sem novo review. Correção mínima: extrair da versão revisada para um arquivo novo, conferir o hash e só então substituir. Por exemplo:

```bash
git show <sha revisado>:docs/devops/102-k309-pre-push-proposto.md | awk '/^```bash pre-push$/{f=1;next} /^```$/{f=0} f' > .githooks/pre-push.novo && echo "<sha256 publicado>  .githooks/pre-push.novo" | sha256sum -c - && bash -n .githooks/pre-push.novo && chmod +x .githooks/pre-push.novo && mv .githooks/pre-push.novo .githooks/pre-push && git diff --stat -- .githooks/pre-push
```

Na falha, apagar `.githooks/pre-push.novo`; o `.githooks/pre-push` original fica intacto. O sha256 do bloco atual é o citado no parecer. Se o bloco mudar, o hash publicado muda junto e o review confere os dois. O comando de voltar atrás (`:352`) está correto e não muda.

**A2, recomendado (baixa; P; devops-engineer).** Evidência em `:23` e `:53`: remoção não passa pela checagem de fast-forward nem pela lista de nomes. Sonda: `feature/r` com amend; `--force` recusado; `--delete feature/r` aceito; `git push origin feature/r` aceito; o remoto saiu de `677f72d0` para `8afdc062`, sem o commit anterior. A remoção de `homolog` também passou pelo hook (a de `develop` só falhou no remoto de teste, por ser a branch atual do bare). O caminho exige dois envios deliberados, como um `--no-verify`, e a proteção do GitHub barra a remoção de develop e homolog. Por isso não bloqueia. Correção: na remoção, recusar `refs/heads/develop` e `refs/heads/homolog` (a main já é recusada), e dizer na seção "Observações para o dono" que apagar e recriar uma branch de trabalho fica fora do alcance de um hook sem estado.

**A3, recomendado (baixa; P; devops-engineer).** Evidência em `:31`: `merge-base --is-ancestor` aceita tag movida para a frente. Sondas: `v1` leve e `v2` anotada, movidas com `git tag -f` para um commit descendente e enviadas com `--force`; as duas passaram (`forced update`). O resumo diz "branch e tag movida" e o caso 14 só cobre commit não descendente. Uma tag de release movida muda o que ela identifica. Correção: em `refs/tags/*` com `remote_sha` não zerado e `local_sha` não zerado, recusar sempre, com a mensagem atual de "mover a tag".

**A4, recomendado (baixa; P; devops-engineer).** Evidência em `:47`, onde `refs/tags/?*` aceita qualquer nome. Sonda: `HEAD:refs/tags/develop` e `HEAD:refs/tags/main` aceitos. Num clone novo, `git rev-parse develop` avisa "refname 'develop' is ambiguous" e devolve o commit da tag, não o da branch. Daí em diante, um `git merge develop` ou `git push origin --delete develop` passa a agir sobre a tag ou falha por ambiguidade. É engano de agente, não ataque externo, porque o GitHub continua mesclando pela branch. Correção: recusar `refs/tags/main`, `refs/tags/develop`, `refs/tags/homolog`, `refs/tags/HEAD` e as tags que começam por um dos prefixos da lista de nomes: `feature/`, `fix/`, `docs/`, `chore/`, `hotfix/`, `refactor/`, `forge/upgrade-`, `test/`, `integracao/`.

**A5, recomendado (baixa; P; devops-engineer).** Evidência em `:27` e `:31`. Sonda: depois de `git replace --graft HEAD <commit remoto>` num commit reescrito, `git push --force origin feature/g` passou pelo hook. O remoto foi para `86ad1553` e deixou de conter `ef7edd02` (conferido com `--no-replace-objects`). Montar o caminho exige um passo deliberado, equivalente a pular o hook. A correção, porém, custa duas palavras: `git --no-replace-objects cat-file -e` e `git --no-replace-objects merge-base --is-ancestor`. O modelo do Forge 0.46.0 tem o mesmo comportamento, e por isso A3 e A5 valem também como contribuição à fábrica.

**Informativos, sem cartão.** (1) Branch com caractere de controle bidirecional (U+202E) no nome, em `feature/`, é aceita e aparece invertida no terminal. O git só recusa caracteres de controle ASCII, e o impacto fica na leitura humana. (2) Diferente do modelo do Forge (`templates/projeto/.githooks/pre-push:56`), o hook proposto não faz `unset GIT_DIR GIT_INDEX_FILE GIT_WORK_TREE` antes do lint. O atual também não faz, então não há regressão. (3) O bloco do Siegard lê `siegard.json` da árvore com separação de palavras sem aspas. Isso está inalterado e fora do escopo.
