## Detalhe dos achados
**A6, recomendado (baixa; esforço P; dono: devops-engineer).** Evidência em `:69`: a lista de tags com nome de branch não cobre o prefixo do remoto. O git resolve o nome curto nesta ordem: `refs/<nome>`, `refs/tags/<nome>`, `refs/heads/<nome>`, `refs/remotes/<nome>`. Por isso a tag `refs/tags/origin/develop` ganha de `refs/remotes/origin/develop` (S5). A tag chega a qualquer clone pelo `clone` ou pelo `fetch --tags`. A partir daí, `git merge origin/develop`, `git rebase origin/develop` e a base `origin/develop` dos scripts `lint-alterados.sh` e `typecheck-alterados.sh` usam o commit da tag. O git só avisa "ambiguous". Os briefs da fábrica mandam `git merge --no-edit origin/<branch>` o tempo todo. Ainda assim, é engano de agente e não ataque externo: o merge no GitHub usa a branch, e quem envia a tag já tem escrita no repositório. Por isso não bloqueia. Sondei `heads/develop` e `remotes/origin/develop` como tag e não há sombra, porque `refs/<nome>` vem antes de `refs/tags/`. Correção mínima: acrescentar `refs/tags/origin/*` ao `case` da `:69`. A lista completa passa a ser `refs/tags/main`, `refs/tags/develop`, `refs/tags/homolog`, `refs/tags/HEAD`, `refs/tags/origin/*`, `refs/tags/feature/*`, `refs/tags/fix/*`, `refs/tags/docs/*`, `refs/tags/chore/*`, `refs/tags/hotfix/*`, `refs/tags/refactor/*`, `refs/tags/forge/upgrade-*`, `refs/tags/test/*` e `refs/tags/integracao/*`. O caso 28 do roteiro ganha `origin/develop`. Se o repositório passar a ter outro remoto, o nome dele entra na lista do mesmo jeito.

**Informativo, sem cartão.** O sha256 garante o bloco apenas para quem confere o comando contra a versão revisada. Quem aplicar a partir de uma versão posterior do documento, com bloco e hash trocados juntos, precisa de novo review. A seção 3 já diz isso ("quem aplica confere que o comando abaixo traz o mesmo valor").
