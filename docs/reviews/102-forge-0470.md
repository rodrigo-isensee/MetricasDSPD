## O que a 0.47.0 muda no fluxo deste projeto
Lido no `CHANGELOG.md` do plugin, seção `[0.47.0] - 2026-11-13`.
- **PR de melhoria só com os pareceres da classe aprovados no head** (`R-REVIEW`, `R-FLUXO`): o PR para a `develop` só abre depois do push e dos pareceres da classe (review, QA e, quando a classe pede, segurança e devops) aprovados no head que vai ao PR, e o CI roda uma vez sobre esse head. Abrir PR só para ver o CI deixa de ser aceito (`docs/fechamento-integrador.md`). Neste projeto isso confirma o passo 4 do `CLAUDE.md` (o PR só abre com o parecer do QA) e o estende aos demais pareceres da classe.
- **`forge-check pr` antes do `gh pr create`, também em rascunho:** o hook `parecer` passa a decidir o `gh pr create`, inclusive com `--draft`, lendo o resultado gravado pelo `forge-check pr <pedido> --ref <branch> --base <base>` para o head, a branch e a base atuais. Sem o aprovado do mesmo head, recusa. Na prática: rodar o `forge-check pr` no head final logo antes de abrir o PR; um commit novo depois exige rodá-lo de novo.
- **Checagem de pareceres como job próprio no CI:** no Forge, os pareceres viram o job `bateria (pareceres)`, fora do `needs` das partes, de modo que parecer faltando reprova o merge sem esconder a suíte; o agregador reprova o job de pareceres pulado ou cancelado em PR. A regra vale para os projetos pela skill `ci-cd` (insumos no `stacks/node-react/pronto.md`). **Este projeto ainda não tem esse job:** o `.github/workflows/ci.yml` não chama o `forge-check pr`, e a conferência dos pareceres hoje é só local (hook no `gh pr create` e `forge-check pr` do integrador). Fica como pendência para o `devops-engineer` (A1), sem efeito sobre este upgrade.
- **`forge-fechar --cartao ID`:** move o cartão para Pronto quando o merge está provado, e o passo 7 poda registros órfãos de worktree; útil aqui, onde o sandbox prende os metadados de worktree.
- **`forge-mutante --base SHA`:** a revalidação roda só os mutantes do diff. Projeto sem `tests/mutantes/` não muda.
- **Modelo com `"ritmo": "equilibrado"`:** projeto sem o campo funciona como `equilibrado`; nada a fazer.
- **Esperar-estado:** subagente segue o teto de 170 s; a sessão principal pode esperar CI longo (e2e) em segundo plano.
